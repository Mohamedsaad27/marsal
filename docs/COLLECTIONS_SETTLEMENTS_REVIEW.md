# مراجعة التحصيلات والتسويات في مشروع Mersal

> **نوع المستند:** مراجعة تقنية ووظيفية شاملة  
> **النطاق:** التحصيلات (`Collections`) والتسويات (`Settlements`) وما يرتبط بهما من الطلبات والأرصدة والتقارير والإشعارات والصلاحيات  
> **تاريخ المراجعة:** 18 سبتمبر 2026  
> **مصدر المراجعة:** السلوك الفعلي في الكود الحالي، وليس الوصف النظري فقط

---

## 1. الملخص التنفيذي

المشروع هو Backend API لنظام لوجستي B2B يربط شركات الشحن بالإدارة ومندوبي التوصيل. الجزء المالي مبني حول مفهومين:

- **التحصيل:** المبلغ الذي يسجله المندوب عند تسليم الطلب أو تحصيل رسوم الشحن أو جزء من قيمة الطلب.
- **التسوية:** تجميع تحصيلات مستلمة نقديًا خلال فترة لطرف محدد، ثم اعتمادها وتسجيل دفعها.

التدفق المنفذ حاليًا هو:

```text
تغيير حالة الطلب إلى حالة مالية
        ↓
إنشاء أو تحديث Collection
        ↓
زيادة رصيد المندوب
        ↓
الإدارة تسجل استلام النقد
        ↓
إنشاء Settlement بحالة Draft
        ↓
اعتمادها Approved
        ↓
تسجيل دفعها Paid
        ↓
ربط التحصيلات + تحديث is_settled + خفض الرصيد
```

التنفيذ منظم من ناحية الطبقات، المسارات، الـEnums، الصلاحيات، الفلاتر، ورسائل API. لكنه لا يحقق حتى الآن دفترًا ماليًا آمنًا للإنتاج؛ لأن النموذج الحالي لا يستطيع تمثيل انتقال المال على مرحلتين من المندوب إلى الإدارة ثم من الإدارة إلى الشركة بطريقة صحيحة، كما أن عناصر التسوية لا تُجمّد وقت الإنشاء.

### التقييم المختصر

| الجانب | التقييم | الملاحظة |
|---|---:|---|
| وضوح الهيكل البرمجي | جيد | Controller → Use Case → Repository → Model |
| تغطية دورة العمل الأساسية | جيد مبدئيًا | إنشاء، اعتماد، دفع، قوائم، إحصائيات |
| العزل والصلاحيات | جيد مع نواقص | عزل المندوب والشركة جيد، وبعض الصلاحيات غير مستخدمة |
| سلامة النموذج المالي | ضعيف | رابط تسوية واحد وتعارض واضح بين مرحلتي التسوية |
| ثبات محتوى التسوية | ضعيف جدًا | المسودة ليست Snapshot ثابتة |
| دقة الأرصدة | ضعيف | منطق زيادة/خصم أرصدة المندوب والشركة غير متسق |
| التدقيق المالي | ضعيف | لا توجد هوية المعتمد أو الدافع ولا Audit كامل |
| التقارير | متوسط | تقارير JSON موجودة، لكن الفلاتر والتصدير ناقصان |
| الاختبارات | ضعيف جدًا | لا توجد اختبارات مباشرة لوحدة Collections/Settlements |
| الجاهزية للإنتاج المالي | غير جاهز | يلزم إصلاح النقاط الحرجة قبل الاعتماد المحاسبي |

## 2. نطاق المراجعة وحدودها

شملت المراجعة:

- وحدة `Collections` كاملة.
- نقاط إنشاء التحصيل داخل وحدة `Orders`.
- جداول `collections` و`settlements` و`order_financials`.
- مسارات الإدارة والمندوب وشركة الشحن.
- حساب العمولة والصافي والأرصدة.
- الصلاحيات والتحقق من المدخلات.
- التقارير والإحصائيات والإشعارات.
- الاختبارات الموجودة والسيناريوهات المفقودة.
- مقارنة السلوك الفعلي مع متطلبات العمل في `docs/business-requirements-mersal.md`.

لا يحتوي هذا المستودع على واجهة React أو تطبيق Flutter الفعليين. الموجود هنا هو Laravel API وصفحة Laravel الافتراضية فقط؛ لذلك المراجعة لا تقيم تجربة شاشة المستخدم أو إدارة الحالة في الواجهة. المرجع المتاح للواجهات الخارجية هو عقود API وملف Postman.

الأدلة:

- التقنيات الأساسية: `composer.json:8-24`.
- ملف JavaScript شبه فارغ: `resources/js/app.js:1`.
- صفحة العرض الافتراضية: `resources/views/welcome.blade.php`.
- متطلبات التدفق المالي: `docs/business-requirements-mersal.md:154-184`.

## 3. نظرة عامة على المشروع

### 3.1 التقنيات

| المكوّن | التقنية |
|---|---|
| اللغة | PHP 8.3+ |
| الإطار | Laravel 13 |
| المصادقة | JWT عبر `tymon/jwt-auth` |
| الصلاحيات | Spatie Laravel Permission |
| قاعدة البيانات | Eloquent + migrations، مع MySQL موثق للإنتاج |
| المعرّفات | UUID للكيانات الأساسية |
| التقارير/Excel | `maatwebsite/excel` موجود، لكن ليس مستخدمًا لتصدير التحصيلات والتسويات |
| الاختبارات | PHPUnit 12 |

### 3.2 النمط المعماري

المشروع Modular Monolith ويحاول تطبيق Clean Architecture. وحدة التحصيلات موزعة على:

```text
app/Modules/Collections/
├── Application/
│   ├── DTOs/
│   ├── Exceptions/
│   └── UseCases/
├── Domain/
│   ├── Enums/
│   └── Interfaces/
├── Infrastructure/
│   ├── Database/Models/
│   ├── Persistence/Repositories/
│   └── Providers/
└── Presentation/
    ├── Http/Controllers/
    ├── Http/Requests/
    ├── Http/Resources/
    ├── Resources/Lang/
    └── Routes/
```

### 3.3 ملاحظة معمارية

الفصل الطبقي جيد تنظيميًا، لكنه ليس Clean Architecture صارمًا:

- واجهات الـDomain تعيد Eloquent Models وLaravel Pagination/Collections.
- `OrderStatusChangeService` موضوع داخل Domain لكنه يعتمد على `DB` وEloquent Models.
- هذا يصعّب الاختبار المعزول ويجعل طبقة المجال مرتبطة بالإطار.

المراجع:

- `app/Modules/Collections/Domain/Interfaces/SettlementRepositoryInterface.php`.
- `app/Modules/Orders/Domain/Services/OrderStatusChangeService.php:14-19`.

### 5.3 قيود قاعدة البيانات الموجودة

نقاط جيدة:

- مفاتيح خارجية بين التحصيل والطلب والمندوب والشركة والتسوية.
- فهارس على حقول البحث والتصفية الأساسية.
- UUID وSoft Delete.
- أعمدة المال من نوع `DECIMAL(15,2)`.
- `order_id` فريد في التحصيلات لمنع تكرار سجل الطلب نفسه.

قيود مفقودة:

- لا يوجد `CHECK` يفرض وجود مندوب فقط لتسوية المندوب أو شركة فقط لتسوية الشركة.
- لا يوجد `CHECK` لقيم النوع والحالة على مستوى قاعدة البيانات.
- لا يوجد `CHECK` يثبت أن `net_amount = total_collections - total_commissions`.
- لا يوجد منع للمبالغ السالبة أو لعمولة أكبر من التحصيل.
- لا يوجد منع لتداخل فترات التسويات لنفس الطرف.
- لا يوجد قيد فريد مناسب على مرجع الدفع.

## 6. دورة التحصيل بالتفصيل

### 6.1 متى يُنشأ التحصيل؟

الحالات التي تتطلب بيانات تحصيل هي:

| حالة الطلب | القيمة | السلوك |
|---|---:|---|
| Delivered | 5 | إنشاء التحصيل مباشرة |
| Delivered Price Changed | 6 | انتظار الموافقة ثم إنشاء التحصيل |
| Partial Delivery | 7 | إنشاء التحصيل مباشرة |
| Refused Paid Shipping | 8 | إنشاء تحصيل رسوم الشحن |

المرجع: `app/Modules/Orders/Domain/Enums/OrderStatusEnum.php`.

### 6.2 التحصيل المباشر

داخل `OrderStatusChangeService::apply()` يحدث الآتي داخل transaction:

1. تحديد الحالة المطلوب تخزينها.
2. تطبيق الآثار الجانبية الخاصة بالحالة.
3. إنشاء أو تحديث التحصيل عند الحاجة.
4. حساب العمولة والصافي على الخادم.
5. زيادة رصيد المندوب بفرق المبلغ الإجمالي.
6. تحديث `order_financials.collected_amount`.
7. تحديث حالة الطلب.
8. إضافة سجل في تاريخ حالات الطلب.
9. إرسال الأحداث بعد انتهاء transaction.

المراجع:

- `app/Modules/Orders/Domain/Services/OrderStatusChangeService.php:28-71`.
- `app/Modules/Orders/Domain/Services/OrderStatusChangeService.php:152-208`.

### 6.3 تغيير السعر

الحالة `DeliveredPriceChanged` لا تنشئ التحصيل فورًا. ينشئ النظام طلب موافقة ويضع الطلب في `AwaitingApproval`. عند الموافقة يُنشأ التحصيل ويُحدث الأثر المالي.

المراجع:

- `app/Modules/Orders/Domain/Services/OrderStatusChangeService.php:130-149`.

## 7. دورة التسوية بالتفصيل

### 7.1 اختيار التحصيلات المؤهلة

التحصيل يدخل التسوية إذا حقق جميع الشروط التالية:

- تم استلام نقده: `cash_received_at IS NOT NULL`.
- لم يرتبط بتسوية: `settlement_id IS NULL`.
- تاريخ `collected_at` داخل الفترة.
- يخص المندوب أو الشركة المحددة وفق نوع التسوية.

المرجع: `app/Modules/Collections/Infrastructure/Persistence/Repositories/SettlementRepository.php:264-278`.

### 7.2 إنشاء المسودة

تُحسب المجاميع على الخادم:

```text
total_collections = SUM(collected_amount)
total_commissions = SUM(commission_amount)
net_amount        = SUM(net_due)
```

ثم تُحفظ التسوية بحالة `Draft`.

مهم: التحصيلات نفسها لا تُربط بالمسودة في هذه المرحلة؛ المحفوظ هو المجاميع والفترة والطرف فقط.

المرجع: `app/Modules/Collections/Infrastructure/Persistence/Repositories/SettlementRepository.php:98-136`.

### 7.3 الاعتماد

يسمح النظام فقط بالانتقال:

```text
Draft → Approved
```

لا يعيد الاعتماد حساب المجاميع، ولا يحجز التحصيلات، ولا يسجل `approved_by` أو `approved_at`.

المرجع: `app/Modules/Collections/Infrastructure/Persistence/Repositories/SettlementRepository.php:139-152`.

### 7.4 الدفع

يسمح النظام فقط بالانتقال:

```text
Approved → Paid
```

عملية الدفع داخل `DB::transaction()` وتستخدم `lockForUpdate()` على التسوية والتحصيلات. داخلها:

1. يعيد النظام البحث عن التحصيلات المؤهلة وفق الفترة والطرف.
2. يربط هذه التحصيلات بـ`settlement_id`.
3. يضبط `order_financials.is_settled = true` للطلبات المرتبطة.
4. يخفض رصيد المندوب أو الشركة بقيمة `settlement.net_amount` المحفوظة.
5. يحفظ طريقة ومرجع ووقت الدفع.
6. يغير الحالة إلى `Paid`.

المرجع: `app/Modules/Collections/Infrastructure/Persistence/Repositories/SettlementRepository.php:154-215`.

## 9. التحقق من المدخلات

### 9.1 نقاط جيدة

- نوع التسوية مقيد بالـEnum.
- `reference_entity_id` يجب أن يكون UUID.
- يتم التحقق من وجود المندوب أو الشركة وعدم حذفهما.
- نهاية الفترة يجب ألا تسبق بدايتها.
- أنواع التحصيل وحالات التصفية مقيدة بقيم معروفة.
- `per_page` في مسارات الإدارة من 1 إلى 100.

المراجع:

### 9.2 نواقص التحقق

- لا يُفرض تطابق نوع التحصيل مع حالة الطلب؛ مثل COD للتسليم الكامل أو Shipping Fee لحالة رفض مع دفع الشحن.

- لا يوجد حد يمنع فترة تسوية مستقبلية أو فترة طويلة جدًا.

- `payment_reference` اختياري وغير فريد حتى للتحويل البنكي.
- لا يوجد تحقق من كفاية الرصيد قبل الخصم.
- لا توجد مطابقة إلزامية بين إجماليات المسودة والتحصيلات الفعلية عند الدفع.

## 14. العيوب والمخاطر

### 14.1 مخاطر حرجة

#### C1. التحصيل الواحد لا يدعم تسوية المندوب ثم تسوية الشركة

**الدليل:** `collections` يحتوي `settlement_id` واحدًا فقط، وكل من تسوية المندوب والشركة تشترط أن يكون هذا الحقل فارغًا.

المراجع:

- `database/migrations/2026_05_19_144502_create_collections_table.php:20`.
- `app/Modules/Collections/Infrastructure/Persistence/Repositories/SettlementRepository.php:264-295`.

**الأثر:** أول تسوية تُدفع تستهلك التحصيل وتمنعه من دخول التسوية الثانية. وهذا يتعارض مع متطلبات العمل التي تصف استلام المال من المندوب ثم تحويل صافي المستحق للشركة.

**الخطورة:** حرجة؛ لأنها تمس تمثيل حركة المال نفسها.

**الحل المقترح:** فصل المرحلتين باستخدام جدول `settlement_items` مع نوع حركة واضح، أو رابطين مستقلين مثل `agent_settlement_id` و`company_settlement_id`. جدول البنود أكثر مرونة وقابلية للتدقيق.

#### C2. المسودة ليست Snapshot ثابتة

**الدليل:** عند إنشاء التسوية تُحفظ المجاميع فقط، بينما إعادة اختيار التحصيلات وربطها يحدثان عند الدفع.

المراجع:

- `app/Modules/Collections/Infrastructure/Persistence/Repositories/SettlementRepository.php:98-136`.
- `app/Modules/Collections/Infrastructure/Persistence/Repositories/SettlementRepository.php:174-186`.

**سيناريو الفشل:**

1. إنشاء مسودة تحتوي منطقيًا على 10 تحصيلات بصافي 9,000.
2. إضافة تحصيل جديد داخل نفس الفترة قبل الدفع.
3. الدفع يعيد الاستعلام فيجد 11 تحصيلًا.
4. يربط 11 تحصيلًا، لكنه يخصم مبلغ المسودة القديم 9,000.

يمكن أيضًا إنشاء مسودتين متداخلتين لنفس التحصيلات، ثم تستهلك إحداهما السجلات قبل الأخرى.

**الخطورة:** حرجة؛ لأنها تسمح باختلاف بنود التسوية عن المبلغ المدفوع.

**الحل المقترح:** إنشاء `settlement_items` وربط البنود داخل transaction وقت إنشاء المسودة، ثم منع استخدامها في أي تسوية متداخلة. عند الاعتماد والدفع يجب التحقق من hash أو مجموع البنود المحجوزة.

#### C3. منطق الأرصدة غير متسق

**الدليل:** رصيد المندوب يزيد بالمبلغ الإجمالي، بينما تسوية المندوب تخصم الصافي فقط.

- الزيادة: `app/Modules/Orders/Domain/Services/OrderStatusChangeService.php:201-203`.
- الخصم: `app/Modules/Collections/Infrastructure/Persistence/Repositories/SettlementRepository.php:194-198`.

**مثال:**

```text
المبلغ المحصل = 1,000
العمولة        =   100
الصافي         =   900

رصيد المندوب بعد التحصيل = 1,000
رصيده بعد خصم التسوية     =   100
التحصيلات غير المسوّاة     =     0
```

يبقى الرصيد 100 رغم عدم وجود تحصيلات غير مسوّاة، بينما ملخص المندوب يعرض الرصيد إلى جانب مجموع التحصيلات غير المسوّاة وكأنهما متوافقان.

أما الشركة، فيتم خصم صافي التسوية من رصيدها، لكن لم يظهر في مسار إنشاء التحصيل ما يزيد `shipping_companies.balance` أولًا.

**الخطورة:** حرجة؛ لأن الرصيد قد يكون خاطئًا أو سالبًا.

**الحل المقترح:** تعريف محاسبي صريح لكل رصيد، ثم استخدام Ledger immutable بدل `increment/decrement` فقط. إذا كان رصيد المندوب يعني النقد الذي يحمله، فيجب خفضه بالمبلغ الإجمالي عند استلام الإدارة للنقد، لا بصافي الشركة عند دفع التسوية.

#### C4. إعادة إرسال نفس الحالة قد تمحو إثبات استلام النقد

**الدليل:** تحديث التحصيل المفتوح يعيد تعيين `cash_received_at` و`cash_received_by` إلى `null`.

- `app/Modules/Orders/Domain/Services/OrderStatusChangeService.php:166-198`.

إذا أعيد إرسال حالة التسليم نفسها بعد استلام الإدارة للنقد، يمكن تعديل المبلغ ومحو بيانات الاستلام. وإذا كان التحصيل مدفوع التسوية، يحاول الكود البحث عن تحصيل مفتوح ثم إدراج سجل جديد، بينما `order_id` فريد، ما قد ينتج خطأ قاعدة بيانات.

**الحل المقترح:** جعل التحصيل غير قابل للتعديل بعد استلام النقد، ومنع إعادة إنشاء أثر مالي لطلب تمت تسويته، واستخدام عملية reversal صريحة بدل تعديل السجل الأصلي.

### 14.2 مخاطر عالية

#### H1. القيم المالية في `order_financials` لا تُحدّث بالكامل في المسار العادي

التحصيل العادي يحدث `collected_amount` فقط، بينما العمولة والصافي المحسوبان يُحفظان في `collections`. مسار موافقة تغيير السعر يحدث حقولًا إضافية، ما يخلق سلوكًا غير متسق بين المسارين.

- `app/Modules/Orders/Domain/Services/OrderStatusChangeService.php:220-230`.
- `app/Modules/Orders/Application/UseCases/Admin/ReviewApprovalRequestUseCase.php:129-134`.

**الأثر:** تفاصيل الطلب وتقاريره قد تعرض عمولة أو صافيًا فارغًا رغم وجود تحصيل صحيح.

#### H2. استيراد طلبات بحالة محصلة لا ينشئ Collection

الاستيراد يمكن أن يملأ `order_financials.collected_amount` لحالات مالية، لكنه لا ينشئ سجلًا في `collections`. التسوية تعتمد على `collections` فقط، لذلك هذه الأموال لا تدخل دورة التسوية.

المرجع: `app/Modules/Orders/Application/UseCases/ImportOrdersFromExcelUseCase.php`.

#### H3. التراجع يترك سجل تحصيل صفريًا

عند نقل الطلب إلى حالة لا تحتاج تحصيلًا، لا يُحذف أو يُعكس التحصيل بحركة مستقلة؛ بل تصفر مبالغه وتُمسح بيانات استلامه.

- `app/Modules/Orders/Domain/Services/OrderStatusChangeService.php:233-267`.

**الأثر:** تضخم عدد التحصيلات، ظهور عناصر مالية بقيمة صفر، وإمكان تسجيل استلام نقد لتحصيل صفري.

#### H4. ضعف حماية العمليات المتزامنة

- `markCashReceived()` لا يستخدم transaction أو `lockForUpdate`.
- `approve()` لا يقفل صف التسوية.
- إنشاء المسودة لا يحجز التحصيلات.

المراجع:

- `app/Modules/Collections/Infrastructure/Persistence/Repositories/AdminCollectionRepository.php:72-85`.
- `app/Modules/Collections/Infrastructure/Persistence/Repositories/SettlementRepository.php:139-152`.

**الأثر:** طلبان متزامنان قد يرسلان إشعارات مكررة أو ينشئان مسودات متداخلة.

#### H5. لا توجد مطابقة مالية قبل الدفع

الدفع لا يعيد حساب المجاميع ولا يقارنها بـ`total_collections` و`total_commissions` و`net_amount`. كما لا يتحقق من أن عدد التحصيلات الفعلي يساوي العدد المتوقع.

**الحل المقترح:** منع الدفع عند أي فرق وإرجاع خطأ reconciliation واضح يطلب إعادة إنشاء التسوية أو مراجعتها.

### 14.3 مخاطر متوسطة

#### M1. التدقيق المالي غير كافٍ

لا يمكن معرفة من اعتمد أو من سجل الدفع من سجل التسوية نفسه. `initiated_by` وحده لا يكفي لفصل الواجبات أو التحقيق في الأخطاء.

#### M2. طرق الدفع غير منضبطة

`payment_method` نص حر، ما ينتج قيمًا غير موحدة ويضعف التقارير. مرجع الدفع اختياري وغير فريد ولا يوجد إثبات دفع مرفق.

#### M3. حالات التسوية محدودة

لا توجد حالات `Cancelled`, `Rejected`, `Failed`, `Reversed`، ولا سبب أو مسار تصحيحي. الخطأ المالي بعد `Paid` لا يمكن معالجته إلا بتعديل مباشر في البيانات.

#### M4. تفاصيل الشركة قبل الدفع غير مكتملة

لأن البنود لا ترتبط إلا وقت الدفع، فإن علاقة `collections` في تفاصيل تسوية الشركة تكون فارغة للمسودة والمعتمدة، رغم عرض عدد مؤهل محسوب ديناميكيًا.

#### M5. استخدام `float` في حسابات مالية

قاعدة البيانات تستخدم `DECIMAL`، لكن بعض الخدمات تحول إلى `float` ثم تستخدم `round`. هذا قد يسبب فروق كسور في عمليات كبيرة أو متكررة.

#### M6. الإشعار النهائي لا يصل للطرف

إشعار الدفع يذهب إلى المديرين فقط. الشركة أو المندوب لا يحصلان على تأكيد نهائي بأن التسوية دُفعت.

#### M7. الصلاحيات المعرّفة لا تتطابق بالكامل مع المسارات

توجد صلاحيات إدارة وتصدير غير مستخدمة، وبعض المسارات تعتمد على الدور بدل الصلاحية. هذا يزيد الغموض عند بناء أدوار مخصصة.

#### M8. أخطاء فلاتر التقارير

التحقق الموحد للحالات يقبل حالات طلبات لتقرير التسويات، وحالة تقرير التحصيلات لا تُطبق فعليًا.

### 14.4 مخاطر منخفضة وتحسينات

- بعض الوثائق الداخلية قديمة وتذكر أن وحدة Collections غير مبنية رغم وجودها.
- لا توجد وثيقة نشر واضحة لتشغيل queues المالية والإشعارات في الإنتاج.
- أمر التطوير يشغل queue عامة، بينما مستمعو الإشعارات يستخدمون queue باسم `notifications` ويجب التأكد من استهلاكها في بيئة التشغيل.
- لا يوجد endpoint واضح لتفاصيل تسوية المندوب رغم إرسال `settlement_id` له في بعض الإشعارات.
- لا يوجد Export فعلي للتحصيلات أو التسويات.

## 15. الفجوة بين متطلبات العمل والتنفيذ

متطلبات العمل تصف التدفق التالي:

1. المندوب يجمع المال من العميل.
2. المندوب يسلم إجمالي التحصيلات للإدارة.
3. النظام يخصم عمولة المندوب.
4. الإدارة تحول المستحق إلى شركة الشحن بعد الاعتماد.
5. النظام يولد كشف حساب تفصيلي لكل طرف.

المرجع: `docs/business-requirements-mersal.md:177-184`.

التنفيذ الحالي يخلط مرحلتي استلام الإدارة من المندوب ودفع الإدارة للشركة داخل مفهوم تسوية واحد ورابط `settlement_id` واحد. النتيجة أن البيانات لا تمثل بوضوح:

- النقد الذي كان بعهدة المندوب وتم استلامه.
- العمولة المستحقة للمندوب وكيف ومتى سُددت أو احتُجزت.
- الالتزام المستحق للشركة.
- التحويل الفعلي للشركة.
- أي عكس أو تصحيح لاحق.

كذلك لا يوجد كشف حساب immutable مبني على حركات؛ الموجود هو أرصدة حالية وتجميعات من سجلات قابلة للتحديث.

## 16. التصميم المالي المقترح

### 16.1 فصل أنواع الحركة

ينبغي فصل العمليتين مفاهيميًا:

| العملية | من | إلى | القيمة المعتادة |
|---|---|---|---:|
| Agent Handover | المندوب | الإدارة | إجمالي التحصيل |
| Company Payout | الإدارة | شركة الشحن | الصافي المستحق للشركة |

إذا كانت العمولة تُدفع للمندوب منفصلة، يجب أن تكون لها حركة ثالثة واضحة. وإذا كانت العمولة تُخصم مما يسلمه المندوب، يجب توثيق ذلك في قاعدة الأعمال وتطبيقه على الرصيد بصورة موحدة.

### 16.2 إضافة `settlement_items`

تصميم مبدئي:

```text
settlement_items
├── settlement_item_id
├── settlement_id
├── collection_id
├── gross_amount
├── commission_amount
├── net_amount
├── created_at
└── unique(settlement_id, collection_id)
```

يُنشأ كل بند وقت إنشاء المسودة داخل transaction. ويمكن إضافة قيد يمنع دخول نفس التحصيل مرتين لنفس مرحلة التسوية.

### 16.3 Ledger للأرصدة

بدل الاعتماد على حقول `balance` المحدثة مباشرة فقط، يوصى بجدول حركات:

```text
financial_ledger_entries
├── ledger_entry_id
├── account_type
├── account_id
├── direction       // debit | credit
├── amount
├── event_type
├── reference_type
├── reference_id
├── occurred_at
├── created_by
└── reversal_of_id
```

الرصيد يصبح ناتج مجموع الحركات، ويمكن الاحتفاظ بـcached balance للأداء مع عملية مطابقة دورية.

### 16.4 دورة حالات أكثر اكتمالًا

```text
Draft → Approved → Processing → Paid
   ↘ Cancelled      ↘ Failed
Paid → Reversed عبر عملية عكس مستقلة
```

لا ينبغي تعديل تسوية مدفوعة. التصحيح يكون بتسوية أو حركة عكس جديدة تحفظ الأثر التاريخي.

### 16.5 فصل الواجبات

يُفضّل دعم قاعدة تمنع المستخدم نفسه من إنشاء واعتماد ودفع التسوية، أو تجعل ذلك إعدادًا قابلًا للتفعيل. الحد الأدنى هو حفظ:

- `initiated_by`, `initiated_at`.
- `approved_by`, `approved_at`.
- `paid_by`, `paid_at`.
- `cancelled_by`, `cancelled_at`, `cancellation_reason`.

## 17. خطة الإصلاح حسب الأولوية

### المرحلة 0: إيقاف المخاطر المباشرة

1. منع تعديل التحصيل بعد `cash_received_at` أو بعد دخوله أي تسوية.
2. منع دفع التسوية إذا تغير عدد أو مجموع التحصيلات عن قيم المسودة.
3. منع العمولة الأكبر من مبلغ التحصيل ومنع صافي سالب.
4. تعريف معنى رصيد المندوب والشركة وتصحيح معادلات الزيادة والخصم.
5. إضافة اختبارات تغطي الأخطاء الحرجة قبل أي تعديل أوسع.

### المرحلة 1: إصلاح نموذج التسوية

1. إضافة `settlement_items` وتجميد البنود وقت الإنشاء.
2. فصل Agent Handover عن Company Payout.
3. ترحيل البيانات الحالية بعناية مع تقرير مطابقة قبل وبعد.
4. إضافة حقول المعتمد والدافع وتواريخها.
5. جعل الاعتماد والدفع idempotent ومحميين بالأقفال.

### المرحلة 2: دفتر الحركات والمطابقة

1. إنشاء Ledger غير قابل للتعديل.
2. اشتقاق الأرصدة أو مطابقتها مع الحركات.
3. إضافة تقرير فروق يومي.
4. إضافة reversal بدل تعديل السجلات القديمة.
5. إضافة قيد إغلاق للفترات المالية عند الحاجة.

### المرحلة 3: تجربة التشغيل والتقارير

1. إضافة تصدير Excel/CSV للتحصيلات والتسويات.
2. إصلاح فلاتر التقارير وفصل Requests حسب نوع التقرير.
3. إضافة مستندات دفع ومرفقات.
4. إرسال إشعار الدفع للطرف المستفيد.
5. إضافة تفاصيل تسوية المندوب وكشف حساب للطرفين.
6. تحديث Postman والوثائق القديمة لتطابق الكود.

| الاختبار | النتيجة المتوقعة |

## 19. معايير قبول النسخة المالية الآمنة

يمكن اعتبار الوحدة جاهزة للاستخدام المالي الفعلي عندما تتحقق الشروط التالية:

- لكل تسوية بنود ثابتة لا تتغير بين الإنشاء والدفع.
- يمكن تمثيل استلام المندوب ودفع الشركة كمرحلتين مستقلتين.
- لا يمكن تعديل تحصيل بعد استلام نقده إلا بعملية عكس موثقة.
- كل رصيد يمكن إعادة بنائه بالكامل من حركات غير قابلة للتعديل.
- كل عملية مالية تحمل هوية المنفذ والوقت والمرجع.
- لا يمكن دفع تسوية إذا اختلفت المجاميع أو البنود.
- العمليات المتزامنة لا تنتج خصمًا أو إشعارًا مكررًا.
- كل endpoint مالي مغطى باختبارات نجاح وفشل وصلاحيات.
- التقارير والقوائم والتصدير تعرض الأرقام نفسها لنفس الفلاتر.
- يوجد تقرير مطابقة دوري يثبت أن الأرصدة والمستحقات متوازنة.

## 20. القرار النهائي

### ما يعمل جيدًا

الوحدة مناسبة كنقطة بداية قوية أو MVP: الهيكل واضح، الـAPI منظم، دورة الحالات الأساسية موجودة، الحسابات تتم على الخادم، وهناك صلاحيات وفلاتر وتقارير وإشعارات وعزل جيد نسبيًا بين المستخدمين.

### ما يمنع الاعتماد الإنتاجي

المشكلات ليست تجميلية؛ أهمها يمس صحة دفتر المال:

1. رابط تسوية واحد لا يمثل التسوية مع المندوب ثم الشركة.
2. التسوية لا تحفظ بنودها وقت الإنشاء.
3. معادلات الأرصدة لا تتوافق مع المجاميع المعروضة.
4. التحصيل المستلم يمكن أن يتغير أو يفقد إثبات الاستلام.
5. لا يوجد Audit واختبارات كافيان لعمليات مالية حساسة.

### الحكم

**الحالة الحالية: صالحة للتجربة الوظيفية، وغير آمنة بعد للاعتماد المالي في الإنتاج.**

الأولوية ليست إضافة شاشات أو تقارير جديدة، بل تثبيت النموذج المحاسبي، تجميد بنود التسوية، فصل المرحلتين الماليتين، وإضافة Ledger واختبارات مطابقة. بعد ذلك يمكن توسيع التصدير وتجربة المستخدم بثقة.
